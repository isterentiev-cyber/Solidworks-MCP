## win32com dynamic dispatch: property vs method — неоднозначность

SolidWorks API отдаёт часть zero-arg членов (`GetTypeName2`, `GetTitle`,
`FirstFeature`, `GetNextFeature`, `IsSuppressed`, `GetType`...) то как
property (значение уже готово при обращении к атрибуту), то как метод,
который надо вызывать `()` — предсказать нельзя, надо проверять эмпирически
через `execute_python`, или лучше — смотреть точную сигнатуру через
`lookup_api_signature` (см. CLAUDE.md).

Наивный фикс `if callable(x): x = x()` **не работает**, потому что
`win32com.client.CDispatch` **всегда** callable (реализует `__call__` для
COM default-member), включая случай, когда `x` — уже готовый результат
(например, следующая фича в обходе дерева). Вызов уже-готового объекта
кидает `(-2147352573, 'Member not found.', ...)`, которая выглядит как
«элементов больше нет» и рвёт обход после первого же элемента. Это и было
причиной сломанных `list_features` (падал на 1 фиче), `get_document_info`,
`list_open_documents` — см. коммит с фиксом (2026-09-07).

`com_get(obj, name)` из `solidworks_mcp/utils/com_helpers.py` — читает
атрибут, и только если результат callable, пробует вызвать, а при ошибке
вызова просто возвращает то, что уже получил. Для методов с аргументами
вызывай напрямую как обычно (`obj.Method(arg1, arg2)`) — там неоднозначности
нет. Методы, возвращающие коллекции/массивы (`body.GetFaces()`,
`body.GetEdges()`), **требуют явного вызова** — они не попадают под
com_get, это настоящие методы.

## Скрин детали + визуальная проверка геометрии

Тул `capture_view` (`automation/capture.py`) — скриншот текущего вида
активного документа в PNG (`doc.SaveBMP(path, w, h)` → конвертация в PNG
через Pillow, т.к. надёжного кросс-версийного PNG-экспорта в SW API нет).
Поддерживает именованный вид (`view="isometric"` и т.п.) и zoom-to-fit.

Рабочий цикл для индексации детали (текстовый поиск по внешнему виду):
1. `capture_view` → путь к PNG.
2. Открыть картинку через `Read` — это и есть "OCR-предположение": модель с
   vision смотрит на форму и словами описывает, что видит (не буквальный
   OCR текста — на 3D-виде обычно текста нет). Для чертежей со штампом/
   размерами, где текст реально есть, отдельного OCR (tesseract и т.п.) в
   проекте нет — не добавлял, пока не появится конкретная задача с текстом
   на изображении.
3. Свериться с фактами из B-Rep-разбора (радиусы/площади граней) — это
   авторитетный источник, картинка только для качественной проверки и
   человеко-читаемого описания.

Пример: деталь `Part Coin Hopper.SLDPRT` по имени файла выглядела как бункер
для монет, но скриншот показал П-образную скобу/ручку — труба + две лапки
с закруглённым торцом, на одной лапке круглое отверстие, на обеих — паз.
Кластеры радиусов (4мм труба+торцы, 2.21мм отверстие, 1мм×4 скруглённые
концы пазов) один-в-один легли на то, что видно на картинке. Вывод: не
доверять имени файла, скриншот — обязательный шаг перед формированием
описания детали.

## Извлечение геометрии тела (B-Rep) — рабочий рецепт

Дерево фич (`list_features`) не показывает скругления/фаски, если они
зашиты в эскиз, а не сделаны отдельной Fillet/Chamfer-фичей. Чтобы найти
реальную геометрию — обход граней/рёбер тела через `execute_python`:

```python
doc = sw.ActiveDoc
body = doc.GetBodies2(0, True)[0]      # 0 = solid bodies, True = visible only
faces = body.GetFaces()                 # метод, нужны скобки
edges = body.GetEdges()                 # метод, нужны скобки

# ISurface.Identity (swSurfaceTypes_e, сверено с swconst.tlb 2026-09-19):
SURF_TYPES = {4001:"PLANE",4002:"CYLINDER",4003:"CONE",4004:"SPHERE",
              4005:"TORUS",4006:"BSURF",4007:"BLEND",4008:"OFFSET",
              4009:"EXTRU",4010:"SREV"}
# (раньше здесь было 4010=EXTRUSION, 4011=REVOLUTION — неверно)
# ICurve.Identity (swCurveTypes_e): 3001 LINE, 3002 CIRCLE, 3003 ELLIPSE,
# 3004 INTERSECTION, 3005 BCURVE, 3006 SPCURVE, 3008 CONSTPARAM, 3009 TRIMMED
# — совпадает с официальным enum. Готовые таблицы: тулы list_faces/list_edges.

for face in faces:
    surf = face.GetSurface          # property, без скобок
    st = surf.Identity
    area_mm2 = face.GetArea * 1e6   # GetArea — property, без скобок
    if SURF_TYPES.get(st) == "CYLINDER":
        radius_mm = surf.CylinderParams[6] * 1000  # [ox,oy,oz,ax,ay,az,radius]
```

Кластеризация радиусов цилиндрических граней = отпечаток отверстий/бобышек/
галтелей, даже когда в дереве нет именованной Fillet/Chamfer-фичи. Конусные
грани (CONE) = фаски. Полный пример разбора — деталь `Part Coin Hopper.SLDPRT`,
2026-09-07.

## Справочная геометрия, масса, ошибки перестроения, правка фич

Добавлено 2026-09-22 (этап 1). Всё проверено на живой детали 60x40x20 мм,
числа сверены вручную.

### create_reference_plane / create_reference_axis

Плоскость: `InsertRefPlane(constraint, value, 0, 0, 0, 0)`, значение в
**метрах** (угол в радианах). Константы `swRefPlaneReferenceConstraint_*`
взяты через `swapi.py find swRefPlaneReferenceConstraint`, не по памяти:
Distance=8, Angle=16, Coincident=4, Parallel=1, Perpendicular=2,
Tangent=32, MidPlane=128, флаг переворота OptionFlip=**256** (складывается
по ИЛИ с основной константой).

`InsertRefPlane` **не отдаёт созданную фичу надёжно**, поэтому результат
берётся из дерева: снимок имён до вызова, разница после. Тот же приём в
осях.

Проверено геометрией, а не фактом «фича появилась» — через
`IRefPlane.Transform.ArrayData` (элементы 9:12 — начало координат,
6:9 — ось Z):

- `reference=front, value=50` → origin (50, 0, 0), нормаль по X;
- `reference=top, value=15, reverse=True` → origin (0, 0, **-15**),
  то есть OptionFlip действительно переносит на другую сторону.

Ось: `md.InsertAxis2(True)` по уже выделенным ссылкам. **Две параллельные
плоскости оси не задают** — `InsertAxis2` возвращает False, тул отдаёт
это текстом, а не молчит.

Ссылки в обоих тулах принимает `select_geom()`: `front`/`top`/`right`
(через `resolve_plane`, не зависит от локали), имя фичи, либо `face:N` /
`edge:N` с индексами из `list_faces` / `list_edges`.

### mass_properties

`IModelDocExtension.CreateMassProperty2()` → `IMassProperty2` (с откатом на
`CreateMassProperty`/`IMassProperty`). **`UseSystemUnits = True`** —
принципиально: иначе значения зависят от того, в чём настроен документ.
Читается СИ, наружу отдаётся г/кг, мм³, мм², г/см³ и мм.

Проверено на блоке 60x40x20 (вручную посчитано и сошлось): объём
48000 мм³, площадь 8800 мм², масса 48 г при плотности 1 г/см³, центр масс
(10, 0, 0), главные моменты 8e-6 / 1.6e-5 / 2.08e-5 кг·м² — все три
совпали с m(a²+b²)/12.

Восемь «инструментов» SW+ из этого блока (mass_kg, volume_mm3,
moment_ixx_mm4 и т.д.) — действительно поля одного вызова, догадка в
SWPLUS-MCP-compare.md верна.

### get_rebuild_errors

Построен на `IFeature.GetErrorCode2()` (обход дерева) плюс проверка
определённости эскизов. `IModelDocExtension.GetWhatsWrong` сознательно **не**
основной источник: у него три by-ref массива на выход, и это ровно тот тип
вызова, который молча отдаёт пустоту. Используется только
`GetWhatsWrongCount` и только как подтверждение.

**Коды ошибок переводятся в имена** через обратную карту `swFeatureError*`
из типобиблиотеки (`feature_error_name`): `code 19` →
`FilletRadiusTooBig2 (19)`. Имя обычно и есть весь диагноз. Незнакомый код
отдаётся числом.

Проверено полным циклом: задал скруглению r=500 на детали толщиной 5 мм →
`ERRORS (1): Fillet2 (Fillet): FilletRadiusTooBig2 (19)` +
`SW GetWhatsWrongCount = 1`; поправил радиус на 2 мм → ошибка ушла,
строка про GetWhatsWrong тоже. Это и есть рабочая петля самопроверки.

Сломать модель оказалось неожиданно трудно: SOLIDWORKS переваривает и
скругление радиусом больше детали, и уменьшение детали под уже построенным
скруглением. Надёжный способ получить ошибку — задать заведомо невозможный
радиус уже существующему скруглению.

### edit_feature

Меняет размеры готовой фичи по **коротким** именам (`D1=30, D2=10`), за
один `EditRebuild3` на все. Ищет по `display_dims(feature)`, принимает и
короткое имя, и полное. После перестроения дописывает дельту объёма и
ошибки фич.

**Важно, чтобы не плодить дубли:** `set_parameter` уже умеет ставить размер
по ПОЛНОМУ имени (`D1@Sketch1`) — ветка `if "@" in name`, а
`get_parameters(feature=...)` уже перечисляет размеры фичи. Отдельные
`set_dimension` / `list_dimensions` из списка SW+ здесь не нужны,
`edit_feature` добавляет короткие имена и пакетную правку.

Не покрыто: правка *определения* фичи (граничное условие вытяжки,
направление, уклон) через `GetDefinition()` → `ModifyDefinition()`. Только
размеры.

## Индекс API (scripts/swapi.py)

Добавлено 2026-09-22. Закрывает дыру, которой у `lookup_api_signature` нет
решения: тот отвечает на «какие параметры у `IFeatureManager.FeatureRevolve2`»,
но только если интерфейс и имя члена уже известны. Из 9788 методов это
тяжёлое стартовое условие, а реальный вопрос обычно обратный — «каким
методом делается оболочка».

```
python scripts/swapi.py find shell          # поиск по всему
python scripts/swapi.py find drawing -k m   # только методы (m/p/c)
python scripts/swapi.py sig IModelDoc2 InsertFeatureShell
python scripts/swapi.py const swEndCondBlind
python scripts/swapi.py build               # пересборка индекса
python scripts/swapi.py stats
```

Что внутри (SW 2026 на этой машине): **9788 методов, 3446 свойств,
8278 констант, 915 интерфейсов**, суммарно ~916 КБ в `api-index/` —
мало для чтения целиком, в самый раз для грепа.

**SolidWorks запускать не нужно, достаточно установленного.** Проверено при
закрытом SLDWORKS.exe: индекс строится из makepy-кэша, а тот генерируется из
зарегистрированной в реестре типобиблиотеки. Практическое следствие: код с
правильными сигнатурами можно писать без CAD; без CAD нельзя проверить только
то, *строится* ли фича на самом деле.

Ранжирование выдачи: сначала совпадения в имени члена, потом в списке
параметров, внутри группы — короткие строки выше. Без этого запрос `shell`
топил `InsertFeatureShell` под `GetShellType` и десятком методов, у которых
слово просто встречается в аргументах. Строки `default_interface` от
CoClass-обёрток из индекса выкинуты — это не вызываемое API.

### Кэш makepy переехал из %TEMP%

Был `%TEMP%\gen_py\<pyver>` — его сносит любая чистка диска, а смена версии
Python осиротит. Теперь `<repo>/.gen_py` (переопределяется переменной
`SW_MCP_GEN_PY`). Логика в `utils/typelib.py::_relocate_gen_cache`.

Две грабли, на которые там стоят обходы:

- `gencache` читает `win32com.__gen_path__` при каждом обращении, поэтому
  переприсвоить атрибут достаточно — **кроме** индекса `dicts.dat`, который
  он загрузил ещё при импорте модуля по старому пути. Его приходится
  перечитывать явно.
- `gencache.Rebuild()` по умолчанию печатает прогресс **в stdout**, а там
  живёт протокол MCP. Только `Rebuild(verbose=0)`. Проверено: при полностью
  удалённом `.gen_py` холодная регенерация не роняет в stdout ни байта.

## Фильтр тулов по разделам (SW_MCP_TOOLSETS)

Добавлено 2026-09-22, `solidworks_mcp/toolsets.py`. Схемы всех 50 тулов
уходят в контекст модели при каждом запросе, а по замеру транскриптов в
типовой сессии используется 10-13.

```
SW_MCP_TOOLSETS=sketch,features   -> 40 тулов
SW_MCP_TOOLSETS=analysis          -> 21
SW_MCP_TOOLSETS=core              -> 16
пусто или не задано               -> все 50
```

Разделы: `core`, `select`, `sketch`, `features`, `analysis`. `core` включён
всегда и отключить его нельзя — без `connect_solidworks`, `execute_python` и
lookup-тулов узкий набор превращается в тупик без выхода.

Неизвестное имя раздела игнорируется с предупреждением, набор при этом не
режется. Тул, которого нет в таблице (добавили и забыли классифицировать),
**остаётся видимым** — ошибка в таблице не должна тихо прятать рабочий
инструмент.

Задаётся в `claude_desktop_config.json` в секции `env` нужного сервера.
**Нужен рестарт MCP**: список тулов фиксируется на старте, `reload_api` его
не подхватывает (он не перезагружает `server.py`).

## Не угадывай сигнатуры — используй lookup_api_signature / lookup_api_constant

Раньше в проекте было полно "18 параметров, наверное" — неверно, реальные
сигнатуры (и enum-значения) можно узнать точно через makepy-кэш
типобиблиотеки SolidWorks вместо угадывания по памяти/доке (которая для
многих методов просто не совпадает с тем, что реально ждёт эта инсталляция).
Инструменты `lookup_api_signature`/`lookup_api_constant` (см. CLAUDE.md)
делают это одним вызовом; реализация — `solidworks_mcp/utils/typelib.py`.

Как это устроено внутри (не нужно писать руками — только если сами тулы
почему-то недоступны): типобиблиотека сама лежит в инсталляции SW
(`C:\Program Files\SOLIDWORKS Corp\SOLIDWORKS\sldworks.tlb` + `swconst.tlb`,
видны через `win32com.client.selecttlb.EnumTlbs()` по описанию `"SldWorks
2026 Type Library"` / `"SOLIDWORKS 2026 Constant type library"`). Сгенерированный
из неё Python-кэш (`makepy`) с 2026-09-22 кладётся в `<repo>/.gen_py`
(раньше — `%TEMP%\gen_py\<python-версия>\`, см. § Индекс API про переезд) —
разовая генерация на ~1-2 сек, дальше инстант, переживает рестарт SW, но не
переустановку/апдейт SW или смену версии Python. Коммитить кэш в git не
нужно — он воспроизводимый и специфичен для машины/версии Python.

`makepy.GenerateFromTypeLibSpec((clsid, lcid, major, minor))` с голым
тюплом падает `Library not registered` — нужно передавать сам
`TypelibSpec`-объект из `selecttlb.EnumTlbs()` (у него есть `.dll` путь).

Так нашлись и исправлены (2026-09-08):
- `FeatureRevolve2` — реально **20** параметров, не 18. Пропущенные —
  `OffsetDistance1`/`OffsetDistance2` (идут между `OffsetReverse2` и
  `ThinType`). Теперь это тул `revolve_sketch` в `features.py`/`server.py`.
- `InsertFeatureChamfer` — **8** параметров, не 7:
  `(Options, ChamferType, Width, Angle, OtherDist, VertexChamDist1,
  VertexChamDist2, VertexChamDist3)`. Исправлено в `chamfer_edges`.

## Построение вала/тела вращения

Собрать ступенчатый вал по чертежу (пример: ШВП для EMCOMAT E300) можно
двумя способами:

1. **Цепочка соосных Boss-Extrude** (проще, надёжнее, если revolve по
   каким-то причинам барахлит): эскиз-круг на торце предыдущего цилиндра
   через `SelectByID2("", "FACE", x,0,0,...)` + `InsertSketch2(True)` +
   `CreateCircle` + `FeatureExtrusion2` (23-парам. вызов из `features.py`).
   Координату точки на торцевой грани найти легко: extrude всегда идёт по
   оси, вдоль которой рос bbox предыдущего тела (`body.GetBodyBox()`).
2. **Revolve одним эскизом** (правильный CAD-way, теперь работает) —
   нарисовать полный ступенчатый профиль одной цепочкой линий +
   `CreateCenterLine` вдоль оси, затем `revolve_sketch`. Слишком близкие
   шаги профиля (разница радиусов ~0.5мм) иногда не создают `CreateLine`
   (возвращает `None`) без ошибки — просто объединять такие шаги, не
   форсировать через более короткий сегмент.

## Sketch на цилиндрической (изогнутой) грани — не работает через InsertSketch2

`SelectByID2("","FACE",x,y,z,...)` + `InsertSketch2(True)` **надёжно
работает только для ПЛОСКИХ граней** (торцевые диски, кольцевые уступы —
`ISurface.Identity == 4001`). Для настоящей цилиндрической грани (боковая
поверхность вала, `Identity == 4002`) — `InsertSketch2(True)` тихо
проваливается (`ActiveSketch` остаётся `None`, без ошибки), причём
**независимо** от способа выбора грани: проверено и через координатный
`SelectByID2`, и через прямой `face.Select4(False, selData)` с точкой
прицеливания, и на новом документе, и на пересохранённом файле, и после
полного перезапуска SolidWorks.exe. Это не деградация процесса/файла —
это стабильное поведение среды. Не тратить время на повторную попытку
через `InsertSketch2`/`Select4` на кривой грани — это тупик (пока не найден
обход в лоб).

**Дополнительная ловушка, из-за которой первая попытка выглядела как
плавающий баг**: `ISketchSegment::GetStartPoint2`/`GetEndPoint2` (и вообще
координаты объектов активного эскиза) возвращаются **в локальной 2D
системе координат самого эскиза**, а не в глобальных координатах модели.
Рисуя линию `(0,0)->(0.05,0.03)` на Front/Top/Right и читая назад её
`GetEndPoint2`, получишь `(0.05,0.03,0)` **на любой из трёх плоскостей** —
это ничего не говорит про то, как локальные оси эскиза мапятся на
глобальные X/Y/Z. Чтобы узнать реальную ориентацию плоскости — не читай
точки эскиза, **выдавливай пробный элемент и смотри его `GetBodyBox()`**
(тело живёт в глобальных координатах). Так выяснено для дефолтного шаблона
детали в этой инсталляции: Front Plane → нормаль X; Right Plane → нормаль Y,
локальные оси (X,Z); Top Plane → нормаль Z, локальные оси (X,Y) (не
гарантировано для других шаблонов/языковых версий SW — проверять так же).

**Рабочий обход для шпоночных пазов** (доведён до создания реального паза,
но не до финального безопасного результата — см. ниже): вместо sketch-on-
face создать смещённую опорную плоскость, касательную к валу в нужном
радиусе:
```python
doc.Extension.SelectByID2("Right Plane", "PLANE", 0,0,0, False,0, empty,0)
plane = doc.FeatureManager.InsertRefPlane(8, RADIUS_M, 0, 0, 0, 0)
# 8 = swRefPlaneReferenceConstraint_Distance
```
Дальше — обычный `SelectByID2("PlaneN","PLANE",...)` + `InsertSketch2` (на
референс-плоскости, не на грани тела, работает без проблем).

**Ещё одна ловушка**: `ISketchManager.CreateCornerRectangle` в этой
инсталляции **тихо возвращает `None`** (команда проваливается без
исключения) при рисовании на такой смещённой плоскости — рисуй
прямоугольник как 4 отдельных `CreateLine` по замкнутому контуру, это
работает.

**И ещё одна**: сырые `CreateLine`-вызовы через API подхватывают
автоматический sketch-relation-инференс SW (снаппинг новых точек к
существующим/к осям), из-за чего координаты прямоугольника **тихо
съезжали** к другим значениям, чем заданы (просадка Z-координат до 0).
Фикс — на время рисования отключить автосвязи:
```python
sm.AddToDB = True; sm.AutoInference = False
# ...CreateLine(...)...
sm.AddToDB = False; sm.AutoInference = True
```
После этого фикса прямоугольник получается пиксель-в-пиксель по заданным
координатам (проверено через `sketch.GetSketchPoints2`).

**Где застряло (2026-09-08, не решено)**: `FeatureCut4`/`FeatureCut3`
(26-27 параметров, сигнатура подтверждена через makepy) с этим
прямоугольником-на-смещённой-плоскости режет с правильной **глубиной**
(депту Y уважает), но **не уважает X-границы прямоугольника** — вырезает
по всей длине вала, а не только в диапазоне паза (проверено дважды: на
реальном ШВП — расщепило деталь на 2 тела, откатил через удаление фичи;
на чистом тестовом цилиндре — тот же эффект без расщепления). Опробованные
без успеха варианты `UseFeatScope`/`UseAutoSelect` (True/True даёт неверный
результат выше; любая другая комбинация — `None`, т.е. cut вообще не
создаётся). Не разобрался, почему профиль не ограничивает рез по оси —
возможных направлений для следующей попытки:
- проверить, не считает ли SW сам факт "профиль касается тела только по
  одной линии по Z" (углы прямоугольника при большом смещении лежат вне
  окружности) поводом трактовать весь эскиз как секущую поверхность, а не
  ограниченный контур — попробовать сделать паз (по ширине) настолько узким,
  что все 4 угла прямоугольника гарантированно внутри материала;
- попробовать `FeatureCut` (старый, без версии) или через явный выбор двух
  граней-границ вместо blind-глубины;
- как временный практичный обход — не резать паз в этом инструменте вообще,
  а делать его вручную в SW UI после автогенерации остального тела.

## CreateCircle тихо возвращает None без AddToDB/AutoInference

`ISketchManager.CreateCircle`/`CreateCircleByRadius` в этой инсталляции, как
и `CreateCornerRectangle` (см. выше про шпоночные пазы), **тихо проваливаются**
(`None`, без исключения) при вызове "в лоб" — даже в чистом новом эскизе на
Front Plane, даже в начале координат. Рабочий тул `draw_circle` не знает про
этот обход и потому падает с `[ERROR] Failed - ensure sketch is active`, хотя
эскиз активен. Фикс — тот же, что и для прямоугольника:
```python
sm.AddToDB = True; sm.AutoInference = False
c = sm.CreateCircle(xc, yc, 0, xc+r, yc, 0)
sm.AddToDB = False; sm.AutoInference = True
```
Проверено многократно (8 отверстий подряд в одном эскизе) — деталь
`side-rail.SLDPRT` в проекте Demo, 2026-09-12. `draw_line` этой проблемы не
имеет — линии создаются без обхода.

## FeatureCut3/4 на эскизе, лежащем на референс-плоскости (не на грани тела)

Cut-вырез по эскизу, нарисованному прямо на Front/Top/Right Plane (а не на
грани тела через `create_sketch_on_face`), в этой инсталляции требует
`Dir=True` (3-й параметр) — с `Dir=False` вызов возвращает `None` без ошибки
независимо от `T1`/`Flip`/`UseFeatScope` и т.д. Найдено перебором всех 4
комбинаций `Flip×Dir` — сработала только `(Flip=False, Dir=True)`. Тул
`cut_extrude` этого не учитывает (`Dir` в нём всегда `False`), поэтому для
такого случая резать через `execute_python` напрямую:
```python
fm.FeatureCut3(True, False, True, 1, 0, 0, 0, False, False, False, False,
               0, 0, False, False, False, False, False,
               True, True, True, True, False, 0, 0, False)
```
(`T1=1` = ThroughAll). Проверено на детали `side-rail.SLDPRT`, 2026-09-12.
Не проверено, нужен ли тот же `Dir=True` для cut на грани тела
(`create_sketch_on_face`) — там пока не тестировалось.

## Сборки (IAssemblyDoc): вставка компонентов и мейты через API

Рецепт, доведённый до рабочего результата (панель лестницы, 2 боковины + 8
перекладин на реальных мейтах, `ladder-panel.SLDASM` в проекте Demo,
2026-09-12):

**`AddComponent5(path, 0, "", False, "", X, Y, Z)`** — `X,Y,Z` позиционируют
не origin детали, а **центр её bounding box** в глобальных координатах
сборки. Т.е. итоговая трансляция origin = `(X,Y,Z) - local_bbox_center`.
Проверять через `component.Transform2.ArrayData[9:12]` (translation),
`[0:9]` — 3×3 поворот.

**Фиксация первого компонента**: выделить его (`SelectByID2(...,"COMPONENT",...)`)
и вызвать `doc.FixComponent()` — обычный `IAssemblyDoc` метод, работает
без сюрпризов.

**Имя подобъекта компонента для `SelectByID2`**: `"ИмяФичи@ИмяКомпонента@ИмяСборки"`
— два `@`, третий сегмент обязателен (просто `"Front Plane@side-rail-1"`
без имени сборки тихо возвращает `False`, без исключения). Работает и для
`"PLANE"` (базовые плоскости компонента), и для `"COMPONENT"` (сам
компонент, тогда достаточно `"ИмяКомпонента@ИмяСборки"`).

**`AddMate5(MateTypeFromEnum, AlignFromEnum, Flip, Distance, DistUpper,
DistLower, GearNum, GearDenom, Angle, AngleUpper, AngleLower,
ForPositioningOnly, LockRotation, WidthMateOption, ErrorStatus)`** — 14
входных + 1 out-параметр (`ErrorStatus`, передавать как
`win32com.client.VARIANT(pythoncom.VT_BYREF | pythoncom.VT_I4, 0)`).
Работает сразу, без сюрпризов с числом параметров (в отличие от
Revolve/Chamfer/Cut). `swMateCOINCIDENT=0`, `swMateCONCENTRIC=1`,
`swMateDISTANCE=5` (см. `lookup_api_constant`, не грепать по памяти).
Селектить обе стороны мейта заранее: первая `SelectByID2(..., Append=False,
Mark=1, ...)`, вторая `Append=True, Mark=1`, затем `AddMate5(...)`.

**Мейты между рёбер плоскостей двух копий одной и той же детали** — рабочий
паттерн, чтобы полностью (без остаточных DOF) поставить вторую копию
параллельно первой на заданном расстоянии: 2× `Coincident` между парой
одноимённых базовых плоскостей, ориентированных перпендикулярно направлению
сдвига (например `Right Plane`↔`Right Plane`, `Top Plane`↔`Top Plane`, если
сдвиг вдоль нормали `Front Plane`), + 1× `Distance` между `Front
Plane`↔`Front Plane` на нужную величину. Проверено — DOF=0, `EditRebuild3`
без ошибок.

**Ловушка: выбор грани по координате (`SelectByID2(...,"FACE",x,y,z,...)`)
в сборке неоднозначен, если в этой точке геометрически совпадают/пересекаются
элементы РАЗНЫХ компонентов** — например, деталь-заготовка (`rung`),
вставленная "начерно" в грубую позицию для мейта, случайно оказалась на той
же оси (Y,Z), что и отверстие в другой детали, предназначенное для ДРУГОГО
экземпляра той же заготовки (совпадение чисто по значениям координат,
использованных для расстановки). `SelectByID2` в этом случае тихо хватает
не ту грань, и последующий `AddMate5` возвращает `None` без диагностики.
Итог был виден только визуально (скриншотом) — 2 из 8 перекладин не
встали. **Фикс**: перед мейтингом расставлять "черновые" компоненты так,
чтобы их пробные координаты заведомо не совпадали ни с одним другим
элементом сборки (например, сдвинуть по оси, не участвующей в дальнейшем
мейте — вставить `rung` на `Y=2.0` вместо `Y=0`, раз мейт всё равно её
переставит по концентричности). Общий вывод: при координатном выборе граней
в сборке — всегда держать пробные позиции черновых компонентов в заведомо
"пустом" углу пространства, не полагаться на то, что "непохожие" номера
не совпадут численно.

## Типизированные обёртки (makepy) — ловушки

Контекст (2026-09-19): как только typelib загружен (`lookup_api_signature`
или, с этого дня, старт сервера), win32com начинает отдавать часть объектов
типизированными (`GetBodies2` → `IBody2`, `Dispatch("SldWorks.Application")`
→ `ISldWorks`), а часть — динамическими (`ActiveDoc`). Смесь непредсказуема,
поэтому новый код всё оборачивает сам: `ext.T(obj, "IFace2")`, члены читает
через `ext.v(obj, "Name")` (вызов, если по typelib это метод).

- У типизированной `ISldWorks` `RevisionNumber` — метод: голое чтение
  атрибута «успешно» даже при мёртвом SW → `is_connected` врал. Теперь
  `com_get`.
- `IFeature.GetTypeName2` в typed-обёртке — **метод** (в динамической было
  свойство). `IsSuppressed` — тоже через `v()`.
- `SelectByID2`: typed хочет `Callout=None` (на `VARIANT(VT_DISPATCH)` —
  `TypeError`), динамический — наоборот (на `None` — `DISP_E_TYPEMISMATCH`).
  `ext.select_by_id` пробует оба.
- **`SelectByID2("", "FACE", x, y, z)` возвращает False** даже для точки
  ровно на плоской грани (в обоих режимах). `SelectByRay` работает и
  сохраняет точку выбора — `ext.select_face_at(md, p_mm)` ищет грань через
  `GetClosestPointOn` и стреляет лучом по нормали.
- `InsertRefPlane` возвращает `IRefPlane`, **не** `IFeature` — переименование
  через `T(ref, "IFeature").Name = …` даёт «Type mismatch». Новая фича —
  последняя в дереве. Параметры-double передавать float (0 вместо 0.0 в
  динамическом вызове тоже даёт Type mismatch).
- `IMathUtility.CreatePoint([..])` через typed-обёртку получает мусор
  (1e-311). Преобразования считать самому по `IMathTransform.ArrayData`:
  `p' = (p · R) * scale + t`, R = a[0:9] построчно, t = a[9:12] (`ext.xform`).
- Середина ребра по `Evaluate2((umin+umax)/2)` для прямых может уехать за
  ребро (у линии был mid y=-80 при ребре -40..40): для LINE — среднее
  концов, для остальных — `IEdge.GetClosestPointOn`.
- `MassProperty`: `doc.Extension.CreateMassProperty` в динамическом режиме —
  «свойство», вызов со скобками падает. Через `v()` без разницы.

## HoleWizard5 — карта Value-слотов (проверено SW 2026)

Перед вызовом — выбрать грань **с точкой** (`select_face_at`): отверстие
встаёт в точку выбора. Сигнатура: `(GenericHoleType, StandardIndex,
FastenerTypeIndex, SSize, EndType, Diameter, Depth, Length, Value1..Value12,
ThreadClass, RevDir, FeatureScope, AutoSelect, AssemblyFeatureScope,
AutoSelectComponents, PropagateFeatureToParts)`. `-1` в Value **не**
универсальное «по умолчанию»:

| тип | что работает |
|---|---|
| `swWzdHole` (2), ISO drill sizes (143) | `SSize="Ø6.0"` (с `.0`, символ U+00D8), Value2 = угол сверла (рад), остальные Value = 0. С -1 и through-all → None |
| `swWzdTap` (4), ISO tapped hole (147) | Diameter = сверло под резьбу, Depth = глубина сверла, **Value1 = глубина резьбы**, остальные -1 (Value6=0 или Value1=0 → дюймовый профиль 25.4 мм + warning). Диаметр резьбы берётся из SSize |
| `swWzdCounterBore` (0), ISO 4762 (139) | Diameter=-1, все Value=-1 → правильные ISO-посадки (M5: Ø5.5 / Ø10×5.4) |

После создания резьбового отверстия через `IWizardHoleFeatureData2`
(`AccessSelections` → поля → `feature.ModifyDefinition(data, md, None)`):
- HoleWizard5 всегда строит «remove thread» (Type 31: ступень Ø-major на
  глубину резьбы). Косметическая: `Type = swTapBlindCosmeticThread` (46) /
  `swTapThruCosmeticThread` (48), `CosmeticThreadType = 1`.
- Угол сверла у резьбы ни один Value-слот не задаёт (выходит ~0.3° — игла на
  7 мм): `DrillAngle = radians(118)` **отдельным** ModifyDefinition — смена
  Type в том же вызове сбрасывает угол.
- Позиции: первый подэскиз фичи — точки размещения, второй — профиль
  вращения. Доп. точки — `EditSketch` первого + `CreatePoint` в координатах
  эскиза.

## Определённость эскизов (sketch_entities / add_sketch_relation / add_sketch_dimension)

Правило: эскиз, который ведёт фичу, должен быть **полностью определён** —
иначе это не параметрическая модель, а геометрия «где нарисовалась».
`delta` предупреждает, если новая фича стоит на недоопределённом эскизе.

- Статус: `ISketch.GetConstrainedStatus()` — 2 under, 3 fully, 4 over, 5 no
  solution. Сущности: `GetSketchSegments()` (тип 0 line, 1 arc/circle),
  `GetSketchPoints2()`; начало координат в эскизе —
  `SelectByID2("Point1@Origin", "EXTSKETCHPOINT")`.
- Связи: выбрать сущности (`ISketchSegment/ISketchPoint.Select4`) →
  `md.SketchAddConstraints("sgCONCENTRIC")` и т.п. Для двух точек
  горизонталь — `sgHORIZONTALPOINTS2D`, для линии — `sgHORIZONTAL2D`.
- Размеры: выбрать → `AddDiameterDimension2 / AddHorizontalDimension2 /
  AddVerticalDimension2 / AddRadialDimension2 / AddDimension2(x,y,z)` —
  координаты текста модельные. Перед этим выключить диалог ввода значения:
  `SetUserPreferenceToggle(swInputDimValOnCreate=10, False)`.
- Две окружности, нарисованные в одну точку центра, получают общий центр
  (P1 один) — concentric уже по факту.
- Привязка размера к переменной (уравнение + EvaluateAll) **выкидывает SW из
  режима редактирования эскиза** — тул возвращает эскиз (`EditSketch`).
- `GetFirstDisplayDimension` у фичи без размеров отдаёт int 0 вместо
  Nothing — makepy падает с `'int' has no attribute GetTypeInfo`. Обёртка
  `ext.display_dims()`.
- **`T(obj, "IFeature")` для ISketch не работает** даже с QueryInterface: QI
  проходит, но IDispatch всё равно диспетчит по таблице ISketch (`.Name`
  вернул кортеж-трансформацию). Фичу эскиза искать по COM-идентичности
  (`ext.sketch_feature`). Общий вывод: T() надёжен только для «своего»
  интерфейса объекта.

## Revolve вокруг оси вне эскиза

`FeatureRevolve2` без осевой линии: эскиз Mark 0 + ось (ось-фича, ребро)
**Mark 4**. Не нужно определять осевую линию в эскизе. Ось `InsertAxis2` из
двух плоскостей смотрит в **-Z** → 90° уходит в -Y; поправить можно без
пересоздания: `IRevolveFeatureData2.ReverseDirection` + `ModifyDefinition`.
Ось создавать ДО выбора эскиза (создание сбрасывает выбор).

## Фаска на кромке тор/плоскость

`InsertFeatureChamfer` на кромке торца гнутой трубы строит грань **BSURF**
(сплайн), а не конус — сторона по тору меряется вдоль кривой поверхности.
Это нормально; торец проверять по площади кольца (1×45 на Ø21.3 → кольцо до
Ø19.3).

## Известные открытые вопросы

- Feature `GetTypeName2` иногда возвращает нестандартные имена — например
  `"ICE"` для **и Boss-Extrude, и Cut-Extrude** (не специфично для типа
  фичи, видимо общее имя для "фича из эскиза" в этой версии SW). Не тратить
  время на угадывание, что это означает буквально.
